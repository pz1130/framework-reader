## 1. 产品定位

**给中文安全团队用的国际框架工作台。**

目标用户：出海企业、外资在华机构、跨国组织中，需要应对 ISO / NIST / PCI / DORA / NIS2 等国际框架的中文安全与合规团队。

差异化不在语言翻译，在**语境翻译**：审计员期待什么、"适当的"到底多适当、这条在实践中通常拿什么当证据、不同地区审计员的松紧差异。这些是资深 CISO 的隐性知识，没有任何标准文本会写。

与 Vanta / Drata / AuditBoard 的关系：不正面竞争。它们英文优先、依赖生产系统集成；本产品中文优先、自托管、不接任何生产系统，服务的是它们覆盖不到的这批用户。

### 已确认的核心决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 产品自带框架知识，用户自带自己的文档（BYO context），不做任何生产系统集成 | 金融/监管行业不会开放生产系统；同时绕开最重的工程量 |
| D2 | 本地 Docker 自托管，LLM 由用户自带 API Key | 敏感文档不出客户环境 |
| D3 | 收入来自**内容包年度授权**，软件本身不是收费点 | 自托管软件收不到经常性收入；内容包的时效性是天然订阅物 |
| D4 | AI 是**离线生产工具与运行时解释器**，不是运行时的事实来源 | 审计场景中"AI 说的"等于"没有依据" |
| D5 | 主骨框架为 NIST CSF 2.0，作为枢纽层的初始内容 | 体量可控、零版权风险、官方 OSCAL 与 CPRT 映射可自由取用 |
| D6 | 路线 A → B → C，A 阶段只生产资产不生产体验 | 资产不会被重写，体验会 |

## 2. 范围

### A 阶段做什么

1. 数据层 schema（SQLite + Pydantic 单一真相源）
2. 骨架导入脚本（OSCAL / CPRT / NIST 署名对照文档）——**不含 SCF、CIS、PCI 官方映射、CSA CCM、第三方 OLIR，见 §4.3**
3. 中文术语表（必须在写第一条解读前定稿）
4. 3 条手写黄金样例
5. AI 初稿生成管线
6. 访谈 TUI
7. 三级深度的内容生产（见 §7）
8. 自动交叉校验 + 反向识别测试
9. 内容包打包 + 构建断言 + 签名
10. 查询壳：CLI + 一个 Claude Code Skill

### A 阶段明确不做（延后，非取消）

| 不做 | 回到哪个阶段 | 为什么不能提前 |
|---|---|---|
| Web UI | B | UI 须围绕成型的数据模型生长 |
| Docker | B | A 阶段只有作者一人使用 |
| 用户可写层（实现） | B | A 阶段无"用户数据"概念；但 schema 现在定义 |
| 文档上传与解析 | C | 依赖 `evidence` 字段作锚点，该字段 A 阶段才产出 |
| 差距报告 | C | 图谱不够厚时报告质量差，会一次性烧掉信任 |
| 问卷代答 | C 之后 | 是差距报告换输入输出，必须复用 C 的解析层 |
| 授权校验 / 收费逻辑 | B 末期 | 无人购买前是零价值代码。注意与 §7.1 的**打包签名**区分：A 阶段产出签名包（证明来源），但不实现到期检查与授权拦截 |

**判据**：某件事若六个月后仍原样存在于最终产品中 → A 阶段做；若会被重写 → 延后。

### 永久不做（会毁掉产品定位）

- 接生产系统自动取证
- 实时威胁情报 / CVE 关联
- 多人协作、工单、任务分派（会变成 GRC 平台，正面撞 Archer / ServiceNow）
- AI 全自动生成制度全文
- 风险量化（FAIR / 蒙特卡洛）
- 供应商风险管理（TPRM）

## 3. 数据模型

### 3.1 结构

```
UnifiedControl          枢纽层，本产品自有概念，不属于任何框架
     ▲
     │ Mapping (带 provenance)
     │
FrameworkControl        某框架下的具体条款
     ├── Interpretation   中文解读（核心资产，本产品版权）
     ├── EvidenceHint     通常拿什么当证据
     ├── AuditorQuestion  审计员会追问什么
     └── Applicability    适用条件（Scoping 用）

OriginalText            单独表；【永远为空】——内容包为空，用户库也写不进去
                        （2026-08-24：注入路径已按网页服务化设计 §7(A) 永久封死）
```

### 3.2 三个关键决策

**① 独立的 `UnifiedControl` 枢纽层**

不以任何具体框架作为枢纽。V1 内容上 1:1 复制自 CSF 2.0 的 106 个 subcategory，但 schema 上完全独立。

- 成本：V1 阶段近似为零（复制一份 ID）
- 收益：任何框架改版只需改该框架的映射边，枢纽不动；且 CSF 的 outcome 粒度不适合当所有框架（如 PCI 的 requirement 粒度）的公分母

**② `Interpretation` 与 `OriginalText` 必须分表**

这是法律边界的物理实现。受版权保护的标准原文永不进入仓库、内容包或 Git 历史。分表使"打包内容包"这一动作在代码层面不可能携带原文，而不依赖人为记忆。

**③ `provenance` 挂在边上，不是表上**

同一对控制之间的映射，可能 NIST CPRT 标 L1、由两跳推导得到 L2-推导、人工确认后为 L3。边是有身份的对象。

```
Mapping {
  from, to,
  relation:   equivalent | subset | superset | related | conflicts
  provenance: { level: L1..L4, source, source_version,
                confirmed_by, confirmed_at }
  note:       "两条看着一样，实际差在哪"   # 隐藏的高价值字段
}
```

### 3.3 Provenance 分级

| 等级 | 来源 | 可否进审计交付物 |
|---|---|---|
| **L1 官方直接** | **由 NIST 本人作为作者发布**的映射（CPRT、SP 800-53 Rev5 随附对照文档）、以及框架自身官方附录 | 是 |
| **L2-推导** | 由两条 L1 边**传递推导**得出（如 CSF →800-53→ ISO 27001），非任何机构直接断言 | **否**，须经 L3 确认后方可导出 |
| **L2-公开** | 其他**授权明确允许衍生与商用**的公开交叉表 | 是，须标注来源与授权 |
| L3 人工确认 | 作者或用户点击确认 | 是，记录确认人与时间 |
| L4 AI 推测 | 模型运行时推理 | **否，默认不进任何导出物** |

**⚠️ L1 的定义已收紧**：仅限 NIST 自身署名的映射。NIST OLIR 目录中**第三方提交**的映射不属于 L1 —— 见 §4.3。

**为什么 L2-推导 不能直接导出**：传递性在控制映射中并不可靠。CSF 的 outcome 粒度与 ISO 的控制粒度不同，A⊇B 且 B⊇C 不蕴含 A 与 C 的对应关系可用于举证。推导边的价值是**给人工确认提供候选**，不是充当依据。

UI 中 L4 以虚线/灰色显示，旁附「确认」按钮；确认后升级为 L3 并永久固化。用户每确认一条，内容资产就厚一层。

### 3.4 Interpretation 字段

```yaml
intent:        这条到底在防什么风险（不是翻译条文）
plain_zh:      用大白话说它要你干什么
common_myth:   中文团队常见的误解            # 差异化字段
practice:      实践中怎么落地，分成熟度 1/2/3 档
evidence:      审计员通常要看什么形态的东西
auditor_asks:  ["...", "...", "..."]        # 差异化字段
regional_note: 欧洲/美国审计员对这条的松紧差异 # 差异化字段
```

三个差异化字段是通用大模型答得最差的地方，也是收费理由。**若这三个字段填不满，说明该条控制尚未吃透** —— 它们同时是质量卡尺。

每个字段附带 `basis`，取值三选一：`quote:<原文定位>`（依据原文哪一句）、`inferred`（模型推断）、
`practitioner`（作者的从业经验）。三个差异化字段恒为 `practitioner`——盲测未通过时，这是回溯
「哪些字段是人给的、哪些是模型给的」的唯一依据。

## 4. 语料获取与生产流水线

### 4.1 语料授权分层

| Tier | 框架 | 处理方式 |
|---|---|---|
| **A 可完整内置** | NIST CSF 2.0 / 800-53 / 800-171 / AI RMF；EU DORA、NIS2、AI Act（EUR-Lex）；CISA、ENISA 公开文件 | 原文可内置 |
| **B 免费可得但不可再分发** | PCI DSS、CSA CCM、SWIFT CSCF | 只存条款编号 + 自写 label + 自写解读；不存原文。**映射数据的可用性另见 §4.3** |
| **D 商用完全不可用** | **CIS Controls v8**（CC BY-NC-**ND**：禁止商用**且**禁止演绎） | 商业产品中不引入其任何内容或映射；仅在必要时以事实性标识提及控制编号 |
| **C 必须购买** | ISO/IEC 27001、27002、42001；SOC 2 TSC | 只存编号 + 自写 label + 自写解读。~~用户上传自己购买的副本，本地注入~~**2026-08-24 取消**：产品已是联网服务，那份原文会落在我们服务器上。见网页服务化设计 §7(A) |

对外表述：**"我们从不再分发任何标准原文。你已购买的标准，始终只留在你自己手里。"**

### 4.2 五阶段流水线

```
① 骨架导入(自动) → ② AI批量初稿(离线) → ③ 人工审核(瓶颈)
                        → ④ 自动交叉校验 → ⑤ 打包
```

**① 骨架导入（纯脚本，无 AI）**

| 拿什么 | 从哪拿 | 得到 |
|---|---|---|
| CSF 2.0 / 800-53 结构 | `usnistgov/oscal-content` (OSCAL JSON) | FrameworkControl 全量 |
| 官方交叉映射 | **NIST CPRT**：`csf-pf-to-sp800-53r5-mappings.xlsx`（NIST 署名） | Mapping **L1**：CSF 2.0 ↔ 800-53 Rev5 |
| 官方交叉映射 | **NIST SP 800-53 Rev5 随附**：`sp800-53r5-to-iso-27001-mapping`（NIST 署名） | Mapping **L1**：800-53 Rev5 ↔ ISO/IEC 27001 |
| 框架自带对照附录 | 各框架官方附录（如 ISO 27002:2022 与 2013 版对照） | Mapping L1（逐个确认可引用性） |
| **推导** | 上两条 L1 边做传递闭包 | Mapping **L2-推导**：CSF 2.0 ↔ ISO 27001（两跳） |
| ~~NIST OLIR 第三方提交件~~ | ❌ 默认排除，见 §4.3 | — |
| ISO 27002:2022 骨架 | 人工建立 93 个编号 + 自写 label | FrameworkControl（无原文） |

此步跑完即得到一张以 CSF 2.0 为中心的映射图：到 800-53 是 L1 直接边，到 ISO 27001 是经 800-53 的 L2-推导边。R7（2026-08-20，n=30，seed=42）correct 17%（< 30%），这些 L2 边**不构成 ISO 的可用起始覆盖**，也不进入 W4–W5 审核队列——留在图内作隐藏提示、不可导出；ISO 映射改走 L4 初稿 → L3（见 §7.2）。

**注意**：可用的免费映射源比原计划少（§4.3）。剩余的边通过 L4→人工确认→L3 自建，这条产线本来就要建（映射确认），现在承担的量更大。

**② AI 批量初稿（离线，一次性，用最强模型）**

输入 = 控制原文（仅 Tier A 有）+ 图上邻居 + style guide + 术语表 + 3 条黄金样例
输出 = Interpretation 字段 YAML，`status: draft`

硬规则：
- 每字段自带 `basis`，无依据者标 `inferred`
- 数据库层面禁止 `draft` 进入内容包（约束，非约定）

**先手写 3 条黄金样例再批量跑。** 这半天是整个项目投入产出比最高的时间。

**③ 人工审核（瓶颈，为其专门做工具）**

访谈 TUI（见 `docs/superpowers/specs/2026-08-20-w2-interview-pipeline-design.md`）：对三个差异化字段（`common_myth` / `auditor_asks` / `regional_note`）走「AI 提问 → 作者回答 → 严格抽取」，**不是**对 AI 初稿的 `a=通过 / e=编辑 / r=重生成` 逐字段审阅。其余字段仍可走初稿+确认路径。

- 目标 3–5 分钟/条（L-Full）、~1.5 分钟/条（L-Core）
- 落库记录 `reviewed_by / reviewed_at / model_version`

做这个 TUI 不是过度工程：审核速度直接决定项目能否完成，200 行代码换回数十小时。

**④ 自动交叉校验**

- 结构：映射对称性、孤儿控制、必填字段缺失
- 术语：术语表强制一致
- 反向识别测试：见 §10

**⑤ 打包（构建时法律断言）**

```
assert original_text 表为空                    否则构建失败
assert 所有条目 status == approved             draft 一律不打包
assert L4 边被剔除或标记 excluded_from_export
签名 + 版本号 + 变更日志
```

法律边界写成构建断言，而非文档中的注意事项。人会忘，CI 不会。

### 4.3 映射源的授权核实结论（2026-08-19 已查证）

原计划把 Secure Controls Framework 与 CSA CCM 当作免费的 L2 映射种子。**该计划不成立。** 进一步查证后，可用面比第一轮判断的还要窄。

| 源 | 授权 | 结论 |
|---|---|---|
| **NIST 自身署名的映射**（CPRT、SP 800-53 Rev5 随附对照文档） | 美国政府作品，公共领域 | ✅ **可用，L1** |
| 各框架官方对照附录 | 一般允许引用条款编号 | ✅ 可用（逐个确认，R1d） |
| **NIST OLIR 目录中第三方提交的映射** | **无统一授权** | ❌ **默认排除**，见下 |
| **Secure Controls Framework** | **CC BY-ND 4.0**（禁止演绎） | ❌ **不可用** |
| **CIS Controls v8** | **CC BY-NC-ND**（禁止商用**且**禁止演绎） | ❌ **商用完全不可用** |
| **PCI DSS**（PCI SSC Terms） | 未经书面许可，不得发布、分发、复制、制作衍生作品或作非个人用途使用 | ❌ 内容不可用；仅自写解读 + 引用编号 |
| **CSA CCM** | 内部评估免费；商用/再分发/衍生需 CSA 授权（企业会员有折扣，价格需洽谈） | ⚠️ **默认不可用**；若要用需单独谈授权 |

**SCF 的具体障碍**：ND 条款禁止创建衍生作品，且明确包含“利用人工智能基于 SCF 内容生成……衍生内容”；不可修改的核心元素明确列入 **“Mappings to Laws, Regulations and Frameworks”** —— 正是本产品需要的那张表。商用授权为 Tier 1 $25,000/年（限 GRC 平台）或 Tier 2 $200,000/年 + 净销售额 20%，当前阶段不可行。

**🔴 OLIR 陷阱（本轮最重要的发现）**：NIST OLIR **不是一个整体授权的数据集**。NIST 只提供项目基础设施；第三方提交的 Informative Reference 由**提交方自行托管并对内容负责**，NIST 明确表示"这些 Informative Reference 本身不带 NIST 的任何保证或背书"，目录页面也未给出任何统一的版权、许可或再分发条款。

**而 SCF 本身就是 OLIR 的参与方。** 因此"从 NIST 网站下载的映射"完全可能就是 CC BY-ND 的 SCF 内容 —— 换个入口，同一份受限数据。

→ **规则：只导入 NIST 自身署名作者的映射。任何第三方提交的 OLIR 一律默认排除；确需使用时，逐个查证提交方条款并记录在案。** 这条规则必须在导入脚本中以来源白名单实现，不能靠人判断。

**CIS Controls 与 PCI DSS**：二者比 SCF 更严。CIS v8 是 BY-**NC**-ND —— 商用本身就被禁止，不只是衍生；PCI SSC 条款明确禁止未经书面许可的发布、分发、复制、衍生与非个人用途使用。两者在本产品中只能以**自写 label + 自写解读 + 引用条款编号**的形式存在（条款编号属事实性标识），其官方交叉映射一律不引入。

**不走灰色地带**：不采用"原样打包 SCF 为独立文件、由用户本地关联"之类的规避方案。本产品的核心卖点是尊重版权，在此处打擦边球的性价比为负。

**这一结论的净影响是正面的。** 若 SCF 映射可自由取用，每个竞争对手同样可以取用，它就不是护城河而是公共品。它被锁住，意味着愿意干净自建映射资产的一方才真正拥有它。缺失的边走 **L4 → 人工确认 → L3**，每一条都归本产品所有，并随使用复利。

**A 阶段仍导入两跳 L2-推导边**（链干净、可入库），路径是：

```
CSF 2.0  ──L1──▶  SP 800-53 Rev5  ──L1──▶  ISO/IEC 27001
   （NIST CPRT）           （NIST SP 800-53 Rev5 随附对照文档）
           └──────── 传递推导 = L2-推导 ────────┘
```

两跳都是 NIST 署名的公共领域文件，因此这条链完全干净。传递得到的 CSF ↔ ISO 边标为 **L2-推导**，**不可直接导出**（理由见 §3.3）。R7 抽样 correct 17%（< 30%），**这些边不作为 W4–W5 审核队列**，只作隐藏提示；ISO 映射改走 L4 初稿 → 人工 L3（见 §7.2）。

## 5. AI 边界（产品宪法）

> **2026-08-20 修订（B 路线）**：原先此表禁止 AI 为 `common_myth` / `auditor_asks` /
> `regional_note` 三个差异化字段起草，配套的访谈管线（AI 提问 → 作者回答 → 严格抽取）
> 已建成并可用，但**作者的时间不足以支撑 106 条的产出节奏**（见
> `docs/superpowers/notes/w2-first-interview-run.md`）。据此改走 B 路线：解读全部由 AI 撰写。
> 护城河随之从「作者的从业经验」转为「内容图谱 + 出处可回溯 + 中文 + 结构一致」。
> 访谈管线保留、不删除，随时可对个别关键控制补入真人内容。

| | 允许 | 禁止 |
|---|---|---|
| **离线生产** | 生成全部七个字段的解读、映射候选、审计追问 | 直接落库（必须有人签字批准出厂）；**伪造 provenance**——AI 写的字段一律标 `basis: inferred`，不得标 `practitioner` |
| **运行时** | 解释库内已有内容、检索并组织、读用户文档并引用原句 | 生成新映射、编造库内不存在的解读、给出无出处的断言 |

**`basis` 与 `confirmed_by` 是两件事，不得混为一谈：**

- `basis` 记**谁写的**。AI 写的标 `inferred`；作者亲手写或改过的标 `practitioner`。
- `confirmed_by` 记**谁批准出厂**。作者签字表示认可这批内容可以交付，
  **不表示他声称是自己写的**。

这条区分是 B 路线下唯一的诚信约束。破坏它，`basis` 字段就失去全部回溯价值。

运行时三条硬约束：

1. 每个回答必须带 `control_id` 与字段来源，UI 上可点回源
2. **检索不到就说"库里没有这条"**，不得自由发挥。在审计场景中，承认不知道是功能，不是缺陷
3. 引用用户文档必须给出文件名与位置，可跳回原文

## 6. 内容包、版本与授权

### 6.1 只读内容层 / 可写用户层，物理分离

```
content-2026.08.pack     只读 · 签名 · 由作者发布 · 升级=整包替换
        ▲ 引用 control_id
user.db                  可写 · 永不被覆盖 · 用户全部劳动成果
```

升级即替换一个只读文件，用户层零字节改动。

**悬空引用的处理**：框架改版可能删除控制。不删、不改用户数据，标记为 `orphaned`，并在 Delta 报告中告知"你标注过的这条在新版框架中已不存在"。这恰是 Delta Watch 想传达的信息，因此是功能而非负担。

### 6.2 格式

单个 SQLite 文件 + `manifest.json` + 签名，打包为 `.pack`。

选 SQLite 而非 JSON 目录：单文件易分发、免解析可直接查询、跨语言可读、air-gap 场景只需拷贝一个文件。

版本号用 **CalVer**（如 `2026.08`）—— 其价值本质是时效性，语义化版本在此无意义。

### 6.3 授权：签名 + 到期日，不联网校验

```json
{
  "licensee": "...",
  "issued": "2026-08-19",
  "expires": "2027-08-19",
  "frameworks": ["NIST-CSF-2.0", "ISO-27001-2022", "..."],
  "signature": "<Ed25519 签名>"
}
```

启动时验签并检查到期日。**过期不锁数据、不删内容** —— 已安装的包继续可用，仅不再接受更新。对付费企业锁数据是自杀性行为；真正的杠杆是"框架变了你不知道"。

### 6.4 不做 DRM（商业判断）

内容包必然会被复制，这是自托管的代价。接受它，理由：

1. 合规客户不敢使用来路不明的内容包 —— 审计员会追问映射依据、版本、维护者。**签名本身就是客户需要的东西**
2. 护城河是更新节奏，不是加密。盗版包三个月后即过时
3. DRM 的工程量与摩擦，伤害付费客户远多于伤害盗版者

签名的目的是**证明来源**（客户需要），不是**阻止复制**（做不到）。

### 6.5 分层打包

| 包 | 内容 | 用途 |
|---|---|---|
| `core-free` | NIST 全家（公共领域） | 免费获客；也是作者日常自用的那个 |
| `intl-pro` | + ISO / PCI / DORA / NIS2 骨架与映射 | 主力付费包 |
| `ai-gov` | ISO 42001 / NIST AI RMF / EU AI Act | 单卖 |

**免费包必须真的好用，不是阉割版。** 它是验证核心假设的唯一渠道，也是唯一的免费获客手段。

## 7. A 阶段：范围、工期、验证、止损

### 7.1 三级深度

| 深度 | 写什么 | 框架 | 条数 |
|---|---|---|---|
| **L-Full** | 全部七字段 | NIST CSF 2.0（106）<br>ISO 27002:2022（93） | **199** |
| **L-Core** | intent / plain_zh / evidence | ISO 42001 Annex A（~38）<br>NIST AI RMF 核心（~30）<br>DORA 关键义务（~40） | **~108** |
| **L-Skeleton** | 编号 + 自写 label + 映射边，无解读 | 800-53 Rev5、PCI DSS v4.0、NIS2 | 脚本导入（CSA CCM 待 §4.3 / R1 结论） |

**深度可跨框架借用**：映射边使得写透 CSF 的一条后，ISO 对应条通过 L1 边自动获得约 80% 的答案，只需补上该框架特有的差异。因此"扩广度"主要是扩骨架、映射与薄解读，深度靠枢纽层复用。

**800-53 与 PCI 坚决只做骨架**：800-53 实际入库 1196 条、PCI v4.0 有 300+ 条子要求，写解读是无底洞；其价值 100% 在作为映射目标。

**新增工作项**：Tier B/C 框架的 label 不可抄官方标题，须自写。做法为 AI 批量改写 → 人工约 20 秒/条快速过 → 术语表统一。此项容易遗漏，遗漏会在打包断言处被拦截。

### 7.2 工期

| 周 | 内容 |
|---|---|
| W1–W2 | 数据工程 + 术语表 + 黄金样例 + AI 管线 + 访谈 TUI |
| **W3** | CSF 106 条 L-Full 审核完成 → **立即跑第一轮盲测** |
| W4–W5 | ISO 27002 93 条 L-Full + L-Core 108 条 |
| W6 | L-Skeleton 导入 + label 改写 + 校验 + 打包 |

**W2 的方法论修订（见 `docs/superpowers/specs/2026-08-20-w2-interview-pipeline-design.md`）**：
`common_myth` / `auditor_asks` / `regional_note` 三个差异化字段**不由 AI 起草**，改为
AI 提问（每条 3 问）、作者回答、严格抽取。原因：若这三个字段也是 AI 稿，W3 盲测比的将是
「带提示词的大模型」对「裸大模型」，通过线过不去，且无法区分「方法论不成立」与「管线设计错了」。

**§4.3 带来的工期影响**：

- **CSF ↔ 800-53**：NIST CPRT 直接覆盖（L1），不受影响。
- **CSF ↔ ISO 27001/27002**：**没有可用的直接 L1 边**。经 800-53 的两跳 L2-推导边已入库（727 条）；R7 抽样（n=30，seed=42）correct **17%（< 30%）**，见 `docs/superpowers/notes/r7-derived-edge-accuracy.md`。**不要把这 727 条 L2 边当作 W4–W5 审核队列或审计依据。** 它们留在图内作隐藏 L2_DERIVED 提示（不可导出）。W4–W5 的 ISO 映射与 PCI / NIS2 / DORA 同一模式：L4 初稿 → 人工确认升 L3。ISO L-Full 工时只保留写 93 条解读；从预算中去掉「确认一批推导边」。
- **PCI / NIS2 / DORA / CIS**：无任何可用的免费官方交叉表，其边全部走 L4 初稿 + 人工确认。

W6 因此从“脚本导入”变为“脚本导入 + 一轮映射审核”，预留 +3–5 天；若工期被挤压，按 §7.4 砍范围，不延期。

全职约 6 周；业余时间约 10–12 周。

### 7.3 验证：范围可以扩，验证不能等

待验证的假设（**2026-08-20 随 B 路线改写**）：

> **"一个接地的中文框架工作台——有内容图谱、有官方映射、每句话可回溯出处、
> 结构一致——比同行自己开一个通用大模型去问更有用。"**

原假设是「**我的**中文解读比裸问大模型更有用」，其护城河是作者的从业经验。B 路线下解读
由 AI 撰写，该假设不再是本产品的卖点，故改写如上。**护城河也随之变浅**：竞争者可以复制
这个形态，本产品的优势是先做出来、图谱更全、出处更硬。这是一次真实的降级，记录在此，
不粉饰。

> **2026-08-22 改：盲测取消，主副验证对调。**
>
> 原因不是盲测设计得不好，是**评委约不到，而且作者设计这套系统时本来就没打算去约**。
> `w3-blind-test-design.md` §0 早就写明「人约不到就跑不起来，这件事没有技术替代方案」——
> 现在这句话应验了。约不到人 ≠ 验证通过，所以本产品**不再按可售卖的东西推进**，
> 降级为**作者自用工具**（该决定见下方「7.3.1 自用降级」）。
>
> 下面的盲测方案与通过线**原样保留**（工装、题、答案均在 `build/blindtest/42/`，
> 代码在 `src/framework_reader/blindtest/`，未删）。将来若真能约到人，直接可跑。
> 但它**不再是任何东西的关卡**。

**主验证 — 盲测（在 W3 进行，不等 ISO 完成）** ~~主验证~~ **已降为选做（2026-08-22）**

- 抽 10 条控制
- 准备三份答案：(a) 本产品 Interpretation　(b) 裸问通用大模型的输出　(c) 框架原文
- 去除来源标识，找 3–5 位真正做过审计的同行，每条问："下周你要为这条准备审计材料，哪一份对你最有用？"

**通过线（事前定死，事后不得修改）：**
- ≥ 70% 场次选择 (a)
- 至少 2 人**主动**指出以下任一项有价值：`common_myth` / `auditor_asks` / `regional_note`
  三个字段的内容，**或**「能看到这条对应哪些别的框架条款、且对应关系标了出处」这件事

第二条随 B 路线放宽了口径：原先只认那三个差异化字段（因为它们是作者经验的载体），
现在映射与出处也算——那才是 B 路线下真正的差异化所在。**≥ 70% 这条线不动。**

**未通过的处理**：不是转去做 UI。先修解读的提示词与结构；两轮仍不过，说明
「接地 + 结构」不足以构成购买理由，届时要么回到 A 路线（作者亲自写），要么停止。

~~**副验证 — 作者自用日志**：CLI 记录每次调用。连续两周作者本人零调用，是最强的死亡信号。~~
**主验证（2026-08-22 起），且窗口从日历改为事件**：

> **下一次真实的框架 / 审计 / 合规工作发生时**：你想起它了吗？用了吗？
> 没用的话，为什么没用？

改的原因：实测「接下来两周有没有真实场景」，答案是**没有**。
连续两周零调用在没有场景的两周里是误杀，不携带任何信息。往下想一层——
**如果连作者本人两周内都用不到一次，这个工具的真实使用频次本来就低**
（审计季才有峰值）。低频不等于没价值，但低频产品的验证周期天然是事件驱动的，
拿日历窗口去测必然测出零，而那个零什么也不说明。

**判据（事前定死）**：不用它的理由就是死因清单——
「忘了」= 想不起来（形态错）、「太麻烦」= 门槛高（壳错）、
「直接问模型更快」= **核心卖点不成立**（这条等价于原盲测那条止损线，
只是由作者本人在真实场景里回答，而不是由评委回答）。

**日志的作用是防回忆，不是判据。** 回忆在这件事上系统性偏乐观。
自动记录客观事实（时间、子命令、control_id），判断写在手记里：
当时在干什么、解决问题了吗、没有这个工具你会怎么办。
第三问是整件事的核心，它是那条止损线的自测版。

**这个判据的弱点必须记下来，不粉饰**：作者既是被试者又是记分员，
且已有沉没成本。它降低自欺的舒适度，消除不了自欺。

### 7.3.1 自用降级（2026-08-22 已决）

**这个产品不再按「要卖的东西」推进。** 验证关卡从「3–5 位同行的盲测」换成
「作者自己用两周」。这是一次诚实的降级，理由与代价都记在这里，不粉饰：

- **失去的**：核心假设（「比同行自己问大模型更有用」）**永远不会被外部检验**。
  自用得住只能证明「对作者有用」，证明不了对别人有用。任何将来的商业化都必须先补这一课。
- **换来的**：不再需要为售卖而做的工程——授权签名与到期检查（§6.3）、DRM 判断（§6.4）、
  分层打包（§6.5）、内容包分发流程全部**不做**。§2「A 阶段做什么」第 9 项里的「签名」
  一并去掉；**打包与构建断言必须留**，它们是 §9 三条红线的机械保障，与售卖无关。
- **内容取舍的判据变了**：从「买家要什么」变成「作者自己会查什么」。
  W4 之后写不写 ISO 93 条、L-Core 108 条，按这条重新判断，不再按覆盖面。
- **R2（职务发明 / 竞业）**：不对外发布、不牟利后风险大幅下降，**不再阻塞**；
  但它只是被推后，不是消失——**转商用之前必须先查清楚**。

**降级后立刻暴露的两个洞**（自用之前必须补，否则「用两周」无从谈起）：

1. ~~**内容包里 `interpretation` 表是 0 行**~~ **已补（2026-08-22）**：草稿也进包，
   `interpretation` 表增 `state` 列，`fr show` 渲出解读并在正文前打
   `[AI 初稿，未经作者确认 · state=draft]`。签过字那批的三道闸门一个没松
   （真签过、签完没被改过、术语表干净）；**草稿的术语表命中只报数不拦**——
   `check_text` 是子串匹配，分不清「地域差异」与「差距分析」，
   拿它拦住整个构建会让工具对作者自己也是空的。实测命中 48 处、涉及 32 条控制，
   签字前需处理。
2. ~~**自用日志根本没实现**~~ **已补（2026-08-22）**：`fr` 每次调用追一行到
   `$FRAMEWORK_READER_HOME`（默认 `~/.framework_reader`）下的 `usage.jsonl`；
   `fr usage` 出报告并把上面三问打出来；`fr usage --note` 追手记。
   **查询类（show/stats）与生产类（draft/interview/blindtest…）分开计数**——
   你在建这个工具不算你在用这个工具，混在一起是最舒服的一种自欺。

### 7.3.2 A 阶段投入到此为止（2026-08-22 已决）

两条验证路径同时没有对象：盲测无评委，自用无场景。§7.4 四条止损线里有三条
**不可能触发**——这意味着从今天起，无论产品好不好都不会有任何信号要求停下。
这比「验证做不了」更危险：前者是不知道答案，后者是不再有人问问题。

**因此停止投入新工时**，只把工具收尾到「那天到来时真的能被用上」：

| 做 | 不做 |
|---|---|
| 自用日志（防回忆） | ISO 27002 93 条 L-Full |
| Claude Code Skill 壳（降低想起它的门槛） | L-Core 108 条（ISO 42001 / AI RMF / DORA） |
| —— | PCI DSS / NIS2 骨架导入 |
| —— | 6 条 `auditor_asks` 缺陷、48 处术语命中（属签字前处理，现在不出厂） |

**扩覆盖面是给买家看的，现在没有买家也没有验证。** 等真用过一次，
你会知道自己缺的是哪个框架——那时候再补，补得准。

已完成的东西不会腐烂：图谱、106 条解读、盲测工装都在 git 里，
放半年再拿出来一行不少。会腐烂的只有继续投进去的时间。

### 7.3.3 自评与差距报告（2026-08-22 已决，§7.3.2 的停止投入随之解除）

§7.3.2 停止投入的理由是「没有任何验证手段」。该条件已变——**作者所在公司要用**，
既做内部提升，也在准备 ISO 27001 认证。场景有了，事件触发的关卡就有了对象，
因此恢复投入，但**只投这一条纵向线**：录现状 → 看差距 → 给下一步。

**「下一步做什么」不需要任何推理。** `practice` 本来就是 1/2/3 三档写好的，
你在 1 档，下一步就是 2 档那段话，配上 `evidence` 就是一条完整的差距项。
这一层唯一做的事是查表、排序、把证据带上——没有模型调用，没有推断。

**一张表两种模式**（`pack/user_schema.sql` 的 `assessment`）：

| 模式 | 用什么 | 给谁 |
|---|---|---|
| 成熟度 | `level` 0/1/2/3 | 有 `practice` 三档的框架（CSF） |
| 适用性声明 | `applicable` + `status` + `reason` | 无解读的框架（ISO Annex A） |

`level` 必须有 **0 档**——`practice` 只写了 1/2/3，没有 0 的话，
大量「压根没做」的条款会被迫虚报成 1 档，报告立刻失真。

**用户数据落 `$FRAMEWORK_READER_HOME/user.sqlite`，绝不落 `build/`。**
`make clean` 会 `rm -rf build/`；自评是几小时的人工投入，不能被一次重建抹掉。
这同时天然满足 §6.1 的内容层/用户层物理分离。

**三条明确不做的：**

1. **不从 CSF 自评自动投射出 ISO 的 SoA。** 那 727 条 CSF↔ISO 边是两跳推导的，
   R7 抽样 correct 17%，§3.3 判定不可导出。把 17% 的东西交给审核员是自毁。
   两个框架各评各的；推导边最多作为**填写提示**出现（标为线索，不进交付物）。
2. **ISO 那 93 条现在没有解读**，只有骨架与自写中文 label，因此 ISO 这边
   暂时只有「适用吗 / 做了吗 / 证据在哪」，没有「下一步做什么」。
3. **ISMS 主条款 4–10 根本不在图谱里。** 库里 ISO-27002-2022 的 97 条是
   4 个大类 + 93 条 Annex A，实测无第 4–10 章。**本工具帮不了拿证**，
   它帮的是把 SoA 那张表填得有据可查。这条必须写明，免得工具制造
   「我在准备认证」的错觉。

**推进顺序（后一步的投入由前一步的结果决定）：**

| 步 | 内容 | 前置 |
|---|---|---|
| 1 | `fr assess` / `fr gap`，先在 CSF 上跑通 | 内容现成，已完成 |
| 2 | SoA 模式 + 可交付导出，跑 ISO 93 条 | ✅ 已完成（2026-08-22） |
| 3 | 写 ISO 93 条解读（原 W4 的活） | 第 2 步确实被用起来 |

**SoA 导出的两条硬规则**（`assess/soa.py`）：

1. **93 条一条都不能少。** 没填的标「待填」摆在表里。漏掉的行不是「没问题」，
   是「没人看过」——一份静默省略的 SoA 比一份填不全的 SoA 危险得多。
2. **提示只在录入时出现，绝不进导出物。** 录入 ISO 某条时会显示它对应到
   800-53 的哪些条款：L1 官方映射标「对应（官方映射）」排在前面，
   L2 推导边标「线索（推导，不可作依据）」。同标题去重——800-53 每个族都有一条
   `-1 Policy and Procedures`，不去重四条提示会是同一句话。

**「由第三方实施」是独立状态，不是「不适用」。** 云厂商或写字楼业主实施的控制
**是适用的**，只是实施者不是你，证据是对方的合同条款或 SOC 2 / ISO 报告。
把它记成不适用是审核员专挑的那类错，而工具如果只给「不适用」这一个出口，
就是在推着人往那个错误上走。状态取值：未开始 / 进行中 / 已实施 / 由第三方实施。

**93 条一次做不完是常态**，因此录入必须能中断续做：已答的自动跳过，
过程中打 `[12/34]` 进度，收尾报「还剩 N 条」。`--function` 改成**前缀匹配**——
CSF 要的是 `DE`，ISO 要的是 `A.7`，而 `A.5.1` 按点切第一段是 `A`，93 条会全中。
ISO 四个主题的实际条数：A.5 37 / A.6 8 / A.7 14 / A.8 34。

第一次自评**不要评 106 条**。106 × 2–3 分钟 ≈ 5 小时，做到第 40 条就会开始敷衍，
后面的数据是垃圾。先评一个 function（DE 11 条，半小时）出第一份报告——
那份报告值不值得把剩下 95 条评完，看完就知道。

### 7.3.4 内容先行发布（2026-08-22 已决）

定位再次改变：目标不是自用工具，是**大众化产品**。§7.3.1「自用降级」与
§7.3.2「停止投入」的前提（不对外发布、不牟利）随之失效，R2（职务发明 / 竞业）
恢复为阻塞项——**已于 2026-08-22 由作者核实，合同无碍**。

**但先发布内容，不先做产品。** 理由：唯一确定的差异化是那 106 条中文解读。
实测 CISO Assistant（AGPLv3、167 个框架库、4.4k star）没有任何中文内容库，
其 ISO 条目的 description 是一句同义反复；而「框架工作台」这个形态它已经做完了，
从正面追是拿三个月换一个免费竞品的复制品。

内容先行的成本与收益：一周内上线、不需要账号 / Web 应用 / Docker、
**不需要约评委**——有没有人看、有没有人问「ISO 的什么时候出」，数据自己会来。
没人要就省下三个月；有人要就有了第一批真实用户，且知道他们要哪个框架。

`fr publish` 从内容包渲一页自包含 HTML（`publish/site.py`）。三条硬规则：

1. **成色写在报头**：106 条全是 `state: draft`，页面必须写明「AI 起草，
   未经逐条人工确认，不要直接当作审计依据交出去」。
2. **只收可导出的映射边**。737 条全部来自 NIST 官方映射文件；
   L2 推导边（correct 17%）一条都不渲。
3. **不转载任何受版权原文**。CSF 2.0 属公共领域，条款编号与英文标题照登；
   ISO / PCI 只字未收——页面上有断言测试钉着这件事。

条款按 CSF 自己的顺序（GV→ID→PR→DE→RS→RC）排，不按字母序。

### 7.3.5 用户导入自己的框架（2026-08-22 已决）

目标形态：**本地部署**，不是托管 SaaS。三条理由——用户上传的是公司安全现状与
内部制度，「数据不出你的网」本身就是卖点；省掉账号、租户隔离、数据合规、备案，
这些跟中文解读这个差异化毫无关系，全是纯成本；起草要调模型，用**用户自己的 key**
（R3 早就定了 BYO key），本地部署天然解决——key 在他机器上，我们不碰、不担责、不垫钱。

**存储分离不动，查询层合起来看。** 导入的框架进用户库（`user_framework` /
`user_control`），内容包一个字节不动——它随时可以 `make build` 重建。但
`QueryAPI` 必须能看见导入的框架，否则它在浏览、自评、差距报告里根本不存在。
做法是 ATTACH 用户库 + 两个联合视图（`all_framework` / `all_control`），
此后一律查视图不查原表。**这件事晚做会波及所有查询，所以第一天就做。**

新增 `LicenseTier.U_USER`：用户自己导入的框架永远不进我们发布的内容包，
也永远不由我们分发。

**导入格式吃 CSV / XLSX**，因为安全团队手上的东西就是 Excel。必需列「编号」
「标题」，可选「上级」「正文」。**坏行一律报错并指出行号，绝不静默跳过**——
静默跳过的结果是用户以为全导进去了。

**「正文」列是这个功能的价值所在。** 只有编号和标题，起草出来的是猜测；带上
用户自己公司的制度原文，起草出来的是基于他实际要求的解读。他的文档、他的机器、
他的 key——与 Tier C/D 的受版权标准原文完全两回事，后者永远不许出网（§9）。

**导入不产生价值，导入 + 自动起草才产生价值。** 只搬编号和标题的话，用户拿到的
是一份目录，等于免费竞品已经给的东西。

### 7.3.6 本地 Web 壳（2026-08-22 已决）

`fr serve` 起一个只监听 `127.0.0.1` 的本地服务。FastAPI + **服务端渲染，不上前端框架**——
第一版不需要那些交互，上 React/SvelteKit 是三个月，服务端渲染是三天。
选型与 §9 表格里「B 阶段用 FastAPI 延续，QueryAPI 不重写」一致。

**Web 层只包一层**：不许写裸 SQL（§8①），也不许有业务判断——否则 Web 与 CLI
会慢慢长出两套行为。有一条测试钉着这件事。

路由：`/` 主页（框架卡片：条数、有解读的比例、内置/导入标记 + 导入表单）、
`/f/{id}` 框架条款列表、`/c/{id}` 条款详情（解读 + 成色标记 + 官方映射）、
`POST /import` 上传、`/f/{id}/assess` 逐条自评、`/f/{id}/gap` 差距报告、
`/f/{id}/soa` 适用性声明（含 `soa.csv` 下载）。

**自评的两种模式由数据决定，不由用户选**：框架有 `practice` 三档就问档位，
没有就问适用性状态。导入的框架起草之前问适用性，`fr draft` 跑完自动改问档位——
用户不需要知道有两种模式存在。

设计令牌抽到 `publish/theme.py`，发布页与 Web 壳共用——分两处写，两处就会长得不一样。

**主页显示「有解读 N/M」不是装饰**：800-53 有 1196 条但一条解读都没有，
点进去是空目录；这件事必须在主页就看得见，而不是点进去才发现。

### 7.3.7 事件触发那道关卡缺一个对照组（2026-08-24 已决）

§7.3 把验证换成事件触发的自问三条，第三问「没有这个工具你会怎么办」是整件事的核心。
**但它现在结构性地答不出来。**

原因是 `.claude/skills/framework-reader/` 这个 Skill 已经全局装好了。作者在 Claude Code
里问「这段制度对应 CSF 哪几条」，模型会自动去跑 `fr search` / `fr show`，查不到的部分
再用自身知识补齐。**「有这个工具」和「没有这个工具」这两种情况，作者在日常里从来不会
分别经历**——没有对照组，第三问只能得到「说不清」。

Skill 是为了降低想起它的门槛而做的（§7.3.2），那个目的达到了；副作用是把唯一的判据
测量掉了。两件事都要，就得把它们在时间上分开：

**定死的做法**：

1. **先在别处问模型。** 不在这个仓库的 Claude Code 会话里问——Skill 会自动触发，
   而且那个会话里的模型已经读过这些解读。用手机 app、网页版或别家的模型，
   问法就是真实工作里会自然问出的那句。
2. **把回答原样存下来**，事后不许重写。那是对照组。
3. **再跑 `fr search` / `fr show`。**
4. **`fr usage --note` 记差**：工具补上了什么、没补上什么，具体到哪条控制的哪个字段。

**不设阈值，也不设次数。** 与 W3 那道闸的区别在于资源性质：3–5 位同行是一次性资源，
问一次就用掉了，所以通过线必须事前定死、事后不得放宽；自用是免费且可重复的测量，
把为一次性资源设计的闸门装到可重复的测量上，是另一种形式的过度设计。
**记录不预设阈值也有价值**——它保住的是「将来想下结论时手里有料」。

**首个触发事件（已确定）**：作者所在公司要写／改一份制度文件，需要对上 CSF 或 ISO
的某几条。见 §7.3.3。

## 8. A → B 接口契约

五项必须在 A 阶段留好，否则 B 阶段需重写。

### ① QueryAPI 抽象，CLI 不得直接写 SQL

```
CLI ─┐
     ├─→ QueryAPI ─→ content.sqlite (只读) + user.db (可写)
Web ─┘
```

CLI 是要扔的，`QueryAPI` 是要留的。CLI 中出现任何一句裸 SQL，B 阶段就要重写查询逻辑。

### ② `control_id` 稳定性契约

> **ID 一经发布，永不复用、永不改变语义。**
> 控制被框架删除 → 标记 `deprecated`，不删行。
> 语义发生实质变化 → 发新 ID，用 `supersedes` 边连回旧 ID。

用户层的全部数据（标注、上传文档、确认过的映射、历史回答）均通过 `control_id` 引用内容层。ID 漂移会使用户多年劳动成果静默指向错误对象，且不会报错。**这是本架构中唯一能造成不可逆损坏的地方。**

### ③ 用户层 schema 现在定义，不实现

```sql
user_annotation(control_id, ...)
user_document(...)
original_text(control_id, ...)          -- 用户注入的标准原文
mapping_confirmation(from, to, confirmed_by, confirmed_at)
answer_history(...)
```

成本约一小时；收益是 B 阶段动手时数据模型已想清楚，且 `QueryAPI` 设计会自然为其留位。

### ④ "确认"是通用机制，只是 actor 不同

A 阶段是作者审核 AI 初稿；B 阶段是用户确认 L4 映射。数据上是同一件事：

```
Confirmation { target, actor, actor_type: author|user, at, model_version }
```

若 A 阶段将审核写成一次性脚本，B 阶段需重做；设计成通用机制则 B 阶段的核心工作流白送。

### ⑤ `locale` 字段从第一天存在

即使 A 阶段只有中文。补字段容易，改主键难。

**A→B 的增量因此很小**：Docker 打包、Web UI（消费已有 QueryAPI）、实现已定义的用户层 schema、内容包安装升级流程。无一项需要触碰内容资产。

## 10. 测试策略

核心资产是内容不是代码，因此分两套。

### A. 代码测试（只测会活下来的部分）

| 测什么 | 怎么测 |
|---|---|
| **打包断言** | 故意往 `original_text` 塞一行 → 构建必须失败。此测试保护法律边界 |
| **ID 稳定性回归** | 仓库存已发布 ID 清单；任何构建若删除或改变已发布 ID 的语义则失败 |
| QueryAPI | 契约测试，B 阶段依赖 |
| 导入 / 映射合并 | 给定 OSCAL / CPRT 样本，验条数、两跳推导的正确性、与 L1/L2 冲突时的优先级 |
| **映射源授权白名单** | 每条 mapping 的 `provenance.source` 必须在**显式允许清单**内。清单以"NIST 署名文件"为单位登记，**不以站点为单位**——`csrc.nist.gov` 不构成允许理由（第三方 OLIR 也在该域名下）。出现 SCF / CIS / PCI 官方映射 / 未授权 CSA CCM / 任何第三方 OLIR → 构建失败 |
| **L2-推导边不得导出** | 任何 `provenance.level == L2-推导` 且未经 L3 确认的边出现在导出物中 → 测试失败 |
| 引用完整性 | 所有 mapping 两端存在、无悬空引用 |
| **Tier C/D 原文不得入模型 payload** | Tier C/D 原文不得进入任何模型调用的 payload。所有 chat client 由 `llm/registry.py` 组装并被 `GuardedClient` 包住，**凡是携带内容的出网只有这一条路径**；命中即抛异常，不重试、不降级、不降为 warn。**2026-08-24 更正措辞**：原文写的是「出网只有这一条路径」，而那句话在 2026-08-23 就已经不精确——`identity/entra.py` 的 OIDC 那时就是第二条。红线要保的是**内容**不外流，不是「进程只准发一个请求」。不携带内容的出网（OIDC、模型目录）各自独立但必须收在可注入替换的 `_default_*` 里，白名单见 `tests/test_no_network_in_tests.py`，取舍见 `docs/superpowers/specs/2026-08-24-model-catalog-design.md` §0 |

TDD 只用于 `QueryAPI`、`pack` 断言、导入解析逻辑 —— 这三块会活到最后。`ingest` / `pipeline` / `review` 大部分是一次性脚本，跑通即可，不追求覆盖率数字。

### B. 内容测试（本产品特色）

1. **反向识别测试**：将 `plain_zh` 单独喂给模型，问"这在描述哪条控制"。Top-1 命中率阈值起步设为 80%，未达标条目打回重写。零成本的质量闸门。
2. **原文零泄漏扫描**：构建时将内容包全文与 `vendor/` 中已购标准原文做 8-gram 重合检测。起始阈值：任一 Interpretation 字段与原文出现 ≥1 处 8-gram 完全重合即报警（实施中按误报率上调 n 或加停用词表）。防止写解读时无意抄录原文片段。`vendor/` 永不进 Git。
3. **术语一致性**：术语表之外的同义词出现即失败。
4. **字段完整性**：L-Full 七字段非空；L-Core 三字段非空。
5. **映射逻辑抽查**：若 A≡B 且 B≡C，而 A—C 标为 `unrelated` → 报警人工复核。

### C. CI 分割

```
公有 CI      → 只跑代码测试；不接触 vendor/，不构建内容包
本地/私有 runner → 内容构建、泄漏扫描、签名、发布
```

签名私钥与受版权原文永不上公有 CI。产品在卖"我们尊重版权"，自己的流水线必须先做到。

## 12. 后续阶段与功能储备

### B 阶段（A 通过验证后）

Docker 打包、Web UI（消费 QueryAPI）、实现用户可写层、内容包安装与升级流程、L4 映射的用户确认工作流、授权与到期检查。

### C 阶段

文档上传与解析、证据匹配、差距报告导出。之后是问卷代答（复用 C 的解析层 + 回答记忆库）。

### 功能储备（按价值/成本比排序，不在 A 阶段）

1. **审计员追问库** —— 每条控制挂 3 个"审计员下一句会问什么"+ 证据形态。已作为 `auditor_asks` / `evidence` 字段并入 A 阶段内容模型。
2. **证据台账（反向映射）** —— 一份证据 → N 条控制。CISO 的痛苦不是不知道要做什么，是同一份东西被要了 8 遍。
3. **适用性向导（Scoping）** —— 帮人少干活比帮人多知道更值钱。依赖 `Applicability` 字段。
4. **框架变更雷达（Delta Watch）** —— 新版发布时 diff 出"你受影响的 N 条"。这是续费的核心理由。
5. **回答记忆库（Answer Library）** —— 上次这题怎么答的、答给谁、谁批的。这是问卷产品真正的护城河。
6. **董事会一页纸** —— 把成熟度态势翻译成 board 能看懂的一页。
7. **"不做会怎样"** —— 每条控制关联处罚区间、真实事故案例、业务影响。CISO 一半的工作是要预算，这给他弹药。
