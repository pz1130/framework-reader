## 0. 形态：一套数据，多个人，按角色分权

**一个组织。** 一个安全团队协作**同一套**材料：同一批框架、同一批解读、同一份自评。

**不是多租户。** 没有多个客户公司共用一套部署，因此不需要客户之间的数据隔离。

这条区分决定整个模型的形状：

> **用户之间不隔离数据，隔离的是「动作」。**

谁都能看见那 93 条 ISO 解读和团队填的自评——那正是协作的意义。区别在于
**谁能改、谁能起草花钱、谁能签字认领**。所以这里要的是 RBAC，不是租户隔离；
是**动作级授权**，不是行级过滤。

这仍然推翻主 spec §7.3.5 的「本地部署」，代价照记：

| 原来省掉的 | 现在要付的 |
|---|---|
| 「数据不出你的网」是卖点 | 卖点没了，你成了这份安全现状的保管方 |
| 不做账号 | 身份、会话、授权、审计，及其全部攻击面 |
| BYO key 在用户机器上 | key 存在服务器上，泄露由你担责 |
| 原文由用户在本机注入 | 见 §7，**唯一剩下的硬前置** |

## 1. RBAC 的五条设计原则

先立原则再排表。表会变，原则不该变。

### 1.1 角色是加法的，不是继承树

一个人可以同时是 `author` 和 `approver`，权限是两者的**并集**。

**不做 `admin ⊃ author ⊃ viewer` 这种继承树。** 继承树的必然后果是「管理员自动
拥有一切」——在这个产品里那恰恰是错的：**管理员能配置系统，不代表他懂这条控制**。
签字确认是专业判断，不该是权限层级的副产品。

### 1.2 权限的单位是「动作」，不是「页面」

权限名形如 `interpretation:confirm`、`framework:import`，不是 `page:control`。

页面上藏起按钮是**体验**，不是授权。同一个动作可能出现在三个页面上；
按页面授权就要在三处各判一次，迟早漏一处。

### 1.3 起草与确认必须能分给两个人

这是这个产品的核心，不是照搬教科书的职责分离。

整套东西的卖点是「**这段话有人认领**」。如果起草的人就是签字的人、签字只是自己
点一下，那么签字在审计员面前没有重量。所以 `author` 与 `approver` 是两个角色。

小团队可以让一个人同时持两个角色——但那是**组织自己的选择**，不是系统替他决定。
系统的职责是让「分开」成为可能，并把这件事记进审计日志。

### 1.4 令牌给身份，我们的库给权限

Entra 的 `roles` claim 只在**登录那一刻**用来同步角色。每次请求的授权判定，
读的是我们自己的 `membership` 表。

理由：令牌会过期、会陈旧。管理员撤掉一个人的 `approver`，必须**立刻**生效，
不能等他的令牌过期。

### 1.5 默认拒绝，且用一条测试钉住

路由没标注权限 → 403，不是放行。

再加一条遍历「**所有路由 × 所有角色**」的测试，逐格比对 §3 的矩阵。
新增路由忘了标注 → 测试红。**这是这套东西唯一不会腐烂的办法**——
权限矩阵靠人记，三个月后必然和代码对不上。

## 2. 角色（四个）

RBAC 的失败方式永远是角色膨胀。这四个各自对应一件**别人不能替你做**的事：

| 角色 | 能做什么 | 存在理由 |
|---|---|---|
| `admin` 管理员 | 管账号与角色、配模型与 key、删框架、看审计日志 | 有人得管系统。**不含确认权** |
| `author` 编辑 | 导入框架、起草解读（花钱）、逐字段改、录自评 | 干活的人 |
| `approver` 确认人 | **签字确认解读、撤销确认** | 认领这段话的人。见 §1.3 |
| `viewer` 只读 | 浏览、导出差距报告与适用性声明 | 给外部审计、给管理层、给刚入职的人 |

**没有 `owner`。** 单组织里它和 `admin` 没有区别，多一个角色只多一层困惑。
「不能把自己锁在门外」用一条不变量解决，不用一个角色解决（§4.3）。

**新账号的默认角色是 `viewer`。** 不是 `author`——默认值决定了忘记配置时会发生什么，
而忘记配置是常态。

## 3. 权限矩阵

`—` = 拒绝。一个人的权限是他所有角色对应列的并集。

| 动作 | 权限名 | admin | author | approver | viewer |
|---|---|:---:|:---:|:---:|:---:|
| 浏览框架与条款 | `content:read` | ✅ | ✅ | ✅ | ✅ |
| 导出差距报告 / SoA | `report:export` | ✅ | ✅ | ✅ | ✅ |
| 导入自有框架 | `framework:import` | ✅ | ✅ | — | — |
| 删除自有框架 | `framework:delete` | ✅ | — | — | — |
| 起草解读（**花钱**） | `interpretation:draft` | — | ✅ | — | — |
| 让 AI 重写字段（**花钱**） | `interpretation:draft` | — | ✅ | — | — |
| 逐字段改解读 | `interpretation:write` | — | ✅ | ✅ | — |
| **确认解读 / 撤销确认** | `interpretation:confirm` | — | — | ✅ | — |
| 录入自评 | `assessment:write` | — | ✅ | ✅ | — |
| 看配套文档 | `document:read` | ✅ | ✅ | ✅ | **—** |
| 传 / 删配套文档 | `document:write` | ✅ | ✅ | — | — |
| 看成员与角色 | `member:read` | ✅ | ✅ | ✅ | ✅ |
| 邀请 / 停用账号 | `member:manage` | ✅ | — | — | — |
| 授予 / 撤销角色 | `role:grant` | ✅ | — | — | — |
| 看模型配置（脱敏） | `model:read` | ✅ | ✅ | — | — |
| 改模型与 key | `model:write` | ✅ | — | — | — |
| 看审计日志 | `audit:read` | ✅ | — | — | — |
| 改内置框架的解读 | — | — | — | — | — |

四条要盯住的：

1. **`admin` 不能起草也不能确认。** 起草花的是组织的钱，确认是专业判断。
   管理员两样都要做，就给自己加 `author` / `approver`——而那一步会进审计日志。
   这正是我们要的：**提权留痕**。
2. **`admin` 不能改解读，但能删整个框架。** 不矛盾：删框架是管理动作
   （导错了、不要了），改内容是专业动作。
3. **「内置框架的解读」整行是空的。** CSF / ISO / 800-53 的解读是产品内容，
   由 `fr draft` 起草、人工评审、进 git。服务端一个写入口都不开——
   `InterpretationStore.save()` 那道门（2026-08-23 已建）在这里同样生效。
4. **起草与重写共用 `interpretation:draft`。** 它们的共同点不是「都用 AI」，
   是**都花钱**。权限的划分依据是后果，不是实现方式。
5. **`viewer` 唯一看不到的东西是配套文档。** 那一档是留给外部审计、管理层、
   刚入职的人的，而上传的是本组织的内部制度**全文**。这与 §9④「viewer 能看
   自评的 note」是同一个问题的两个答案，分歧点在于颗粒度：一句现状说明可以给，
   一整本制度不行。**这是一个判断，不是一条推论**——真有人要给外部审计看全文，
   在这里改一行就是了。
6. **传文档和导入框架不共用权限。** 导入框架是「多一张控制清单」，
   传文档是「把内部制度放上服务器、并让它进模型的 payload」。后果不是一回事。

## 4. 落地

### 4.1 判定点只有一处

```python
@app.post("/c/{control_id}/confirm")
@requires("interpretation:confirm")
def confirm_control(...): ...
```

装饰器从会话取 `account_id` → 查 `membership` → 展开成权限集合 → 判定。
**不查令牌**（§1.4），**不在模板里判**（§1.2）。模板里的 `if` 只决定按钮显不显示；
藏与不藏都不影响授权结果。

### 4.2 遍历测试

```
for 每条路由 in app.routes:
    for 每个角色 in ROLES:
        断言(实际是否放行 == 矩阵[路由][角色])
```

外加一条：**每条写路由都必须标注权限**，没标注的直接让测试失败——
而不是等它在生产上放行。

### 4.3 两条不变量

- **至少留一个 admin。** 撤销最后一个 `admin`、或停用最后一个 admin 账号，
  一律拒绝。否则第一次误操作就把所有人锁在门外，只能改库救
- **不能给自己授予角色。** admin 给别人授权可以，给自己提权要另一个 admin 点头。
  单 admin 的小组织下这条会挡路，所以做成**可关闭的开关**，默认开、关掉要留痕

两条都落在 `IdentityStore`，不在路由层——CLI 也能改角色，判在路由上等于只锁了一扇门。
`grant()` 比的是 `by == account_id`：CLI 传的 `"cli"` 不是任何人的 id，所以
**CLI 始终是那条救场通道**（服务器上还有 shell 的人本来就能改库）。
**只挡 `grant` 不挡 `revoke`**：降权不是提权，而撤到最后一个 admin 有另一条不变量接着。

### 4.4 审计日志

合规产品没有审计日志是不成立的。至少这四类，**不可删除、不可修改**：

| 事件 | 为什么必须记 |
|---|---|
| 授予 / 撤销角色 | 提权是所有事故的第一步 |
| 确认 / 撤销确认解读 | 产品的核心动作，「谁认领的」必须可追溯 |
| 改模型配置 | 换 endpoint = 数据流向变了 |
| 登录 / 登录失败 | 基本盘 |

改解读本身**不**进审计日志——`basis`、`confirmed_by`、`signed_digest`
已经在解读里逐字段记了出处，再记一遍是冗余。

## 5. Entra ID（AAD）

### 5.1 协议

**OIDC Authorization Code + PKCE，机密客户端（服务端持密）。**
不用 implicit（已废弃）、不用 ROPC（要用户密码，与 SSO 的意义相反）。
凭据用**证书**优于 client secret（后者会过期、会被抄进配置文件）。

端点走发现文档，不要硬编码：
`https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration`

### 5.2 id_token 校验（一条都不能省）

| 校验 | 说明 |
|---|---|
| 签名 | JWKS 从发现文档取，按 `kid` 选；**缓存要跟得上轮换**（遇未知 kid 刷新一次，别无限刷） |
| `iss` | 必须等于发现文档里的 issuer |
| `aud` | 必须是我们的 client_id |
| `exp` / `nbf` | 时钟偏移容忍 ≤ 5 分钟 |
| `nonce` | 与授权请求下发的一致，一次性 |
| `tid` | 必须是**你们公司自己**那个 Entra 租户 |

单组织形态下最后一条尤其重要：**应用注册必须是单租户**。
配成多租户的话，**任何** Entra 用户都能走到你的登录回调。

### 5.3 身份

- **主键用 `oid`，不用 email / `upn` / `preferred_username`。**
  后三者会变（改名、换域、别名），拿它们做主键，用户改个名就成了新人、丢掉全部历史
- `email` 只用于显示与邀请匹配

### 5.4 角色怎么来

**用 App Roles（`roles` claim），不要用 `groups`。**

- App Roles 由应用自己定义，管理员在 Entra 里指派，与我们的四个角色一一对应
- `groups` claim 有 **200 个的溢出限制**，超了变成 `_claim_names` 逼你回头调 Graph——
  多一个依赖、多一种失败模式；而且组名是客户 AD 的内部约定，和我们的角色不是一回事

**同步方向定死并写在界面上**：Entra App Role → 我们的 `membership`，
**只在登录时单向同步**。我们这边的手工调整会在该用户下次登录时被覆盖。
不写出来，管理员会以为自己改生效了。

**保留本地邀请制账号**——首个 admin 得有办法进来，Entra 配错时也得有条路。
两条路落到同一张 `membership` 表。

同步有**一个例外**：**不撤最后一个 admin**。Entra 那边少配一个 App Role，
就没人能管系统了——那不能是一次登录的副作用。撤不掉时记 `role.sync_refused`。

先按 `oid` 找人，找不到再按 email **认领**已有账号（那个「先发了邮箱邀请、
人却先走了 SSO」的账号）。不认这条会长出两个同名账号，而谁都说不清哪个是他。
认领的安全前提是 `tid` 已经钉死在自己的租户上——邮箱由自己公司的 AD 管。

### 5.4b 配置从哪来

五个环境变量，`fr entra check` 连一次发现文档并把错的那项指出来：

```
FR_ENTRA_TENANT_ID / CLIENT_ID / CLIENT_SECRET / REDIRECT_URI / AUTHORITY
```

**配了 Entra 就等于锁门**——哪怕一个账号都还没有。接了 IdP 说明这是联网部署，
这时门还敞着，等于第一个走进来的是任何人。

### 5.5 会话

- **服务端会话 + 不透明 cookie**，不是 JWT-in-cookie——要能在服务端立刻撤销
- Cookie：`HttpOnly` `Secure` `SameSite=Lax` `Path=/`，不设 `Domain`
- 绝对过期 8 小时 / 空闲 1 小时；登录时轮换 session id（防会话固定）

`Secure` 不靠部署的人记得传开关：**回调地址是 `https://` 就自动打开**。
漏一次就是会话 cookie 明文过网，而这种漏法不会有任何症状。

登录途中的 `state` / `nonce` / PKCE `verifier` 存在服务端（`oidc_flow` 表），
取出即删、十分钟过期。放 cookie 里的话，那三样每一样泄漏都能拼出一次登录。

## 6b. 配套文档（S5）

起草器写出来的是**通用**的落地建议。这个团队真正的落地方式写在他们自己的
制度里——「日志留存六个月」还是「一年」，是他们文件里的一行，不是模型能猜的。

四条：

- **只收 `.docx` / `.txt` / `.md`。** 每多一种格式就是一条新的解析路径，
  而解析别人的文件是攻击面最集中的地方。**PDF 不收**：扫描件要 OCR、排版件
  切出来的段落是乱的，而**噪声接地比没有接地更糟**——模型会照着乱码编
- **存解析出来的文本，不存原始文件。** 原始文件留在服务器上只是多一份拷贝、
  多一个泄漏面，而起草要用的从来只是文字
- **检索不用向量。** 中文按字符二元组取交集，除以长度的平方根排序。
  不出网、不加依赖、不引入一个「为什么这段没被检索到」谁也说不清的黑盒。
  交集低于阈值就**返回空**——宁可不给，也不给错的
- **自家制度与 800-53 原文在 payload 里分开标注。** 前者说「现在是什么」，
  后者说「应该是什么」。混在一起，模型会把「我们已经这么做了」写成
  「标准要求这么做」——那正好把这个产品的立身之本（哪句话是谁说的）搞坏

配套文档**只给用户自己导入的框架**用（`run.documents_for()`）。内置框架的解读
是我们要发布的内容，里面出现某一家公司的内部制度，既不对，也发不出去。

**顺带修掉的一个洞**：FastAPI 的 `/docs`、`/redoc`、`/openapi.json` 由框架特殊
注册，**绕过 §4.1 那道门**——等于一份不需要登录就能拿到的完整路由清单。已关闭。
